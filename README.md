# owrt-netguard

[English](README.en.md)

Небольшой независимый проект для OpenWrt, который я задумал, чтобы разобраться, почему пропадает интернет и на каком участке возникает проблема.

Идея появилась из вполне практической ситуации: на моих роутерах несколько раз пропадала связь, а диагностика [Podkop](https://github.com/itdoginfo/podkop) сообщала об ошибках DNS. В итоге причиной оказывались неполадки у провайдера. При этом похожие симптомы могут возникать из-за самого роутера, DNS, маршрутизации или VPN — и по сообщению одного сервиса не всегда понятно, с чего начинать поиск.

В OpenWrt уже есть инструменты для проверки доступности, сбора статистики и восстановления соединений. Они решают свои задачи, но мне хотелось другого: сопоставлять проверки на разных уровнях, отличать причину отказа от сопутствующих ошибок и сохранять историю инцидентов. Так появилась идея NetGuard.

Хотя задача выросла из конфигураций с Podkop и VPN, делать ещё один инструмент только для Podkop я не хотел. NetGuard задуман как самостоятельный монитор для разных конфигураций OpenWrt, который со временем можно будет расширить безопасными механизмами восстановления связности.

## Статус

**В репозитории появился первый экспериментальный прототип `owrt-netguard check`. Стабильного релиза и установщика пока нет.**

Это ручная однократная диагностика IPv4, а не фоновый монитор. Прототип только читает состояние OpenWrt и выполняет сетевые запросы; он не перезапускает службы, не меняет DNS, firewall и маршруты.

### Пробная проверка

На роутере с установленным `curl` можно загрузить текущий исходник в `/tmp` и запустить его через shell:

```sh
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/owrt-netguard \
  -o /tmp/owrt-netguard
sh /tmp/owrt-netguard check
```

Временный файл не добавляется в автозапуск и не устанавливается в систему. Если нужного компонента нет, команда завершится с сообщением об ошибке, но самостоятельно ничего устанавливать не будет. Для проверки другого логического WAN:

```sh
OWRT_NETGUARD_WAN=wan2 sh /tmp/owrt-netguard check
```

Прототип использует `ubus`, `jsonfilter`, `ip`, `curl`, `nslookup` с собственными параметрами таймаута (`-timeout`/`-retry`) и стандартные BusyBox-утилиты. `nft` используется необязательно, для проверки попадания адресов в набор Podkop.

Пока реализованы проверка состояния WAN, несколько HTTPS-целей через явно заданные IP с проверкой TLS и несколько независимых DNS-резолверов. Для HTTPS **доступность TLS/HTTP-сервера и исправность контрольного endpoint — разные результаты**: например, HTTP 404 от Яндекса показывает, что сервер отвечает, но не считается успешным контрольным ответом. Строгие проверки сейчас используют Cloudflare (`/cdn-cgi/trace`, HTTP 200) и Google DNS API (`/resolve?name=example.com&type=A`, HTTP 200); Яндекс и Quad9 пока дают только дополнительный сигнал доступности TLS/HTTP, без требования к коду ответа. После двух подтверждённых успешных HTTPS-ответов дополнительные цели не опрашиваются; DNS-проверки аналогично прекращаются после двух ответов. При ошибках опрос расширяется.

Доступные статусы включают `HEALTHY_SAMPLED` (только проверенная выборка, не гарантия доступа ко всему интернету), `PARTIAL_REACHABILITY`, `WAN_NO_L3`, `LOCAL_DNS_UNAVAILABLE`, `EXTERNAL_DNS_UNCONFIRMED`, `DNS_PATH_UNCONFIRMED` и `UNKNOWN_ROUTE`. Недоступные или пропущенные цели не позволяют безоговорочно считать всю сеть исправной.

**Важные ограничения:** в прототипе только IPv4; набор endpoint пока задан в исходнике, а пользовательская конфигурация через UCI запланирована на следующий этап. Доступность проверочных IP в Крыму и других регионах пока не подтверждена. Сбой всех выбранных endpoint не доказывает аварию провайдера. `--interface` и обычная таблица маршрутов не гарантируют обход всех nftables/PBR-правил; внешний DNS-запрос через `nslookup` также не привязан строго к WAN. История инцидентов, уведомления и Recovery не реализованы. На реальном AX6000 под OpenWrt 24.10.5 успешно запускалась **предыдущая** версия прототипа; текущие исправления ещё требуют повторной проверки.

Для OpenWrt 25.12.5 подготовлен [тестовый стенд QEMU](tests/ci/README.md) с ручным запуском GitHub Actions. Workflow ещё не активирован и не запускался; реальных аппаратных испытаний 25.12 также не было.

### Собственные контрольные адреса (необязательно)

По умолчанию используются встроенные HTTPS- и DNS-цели. Их можно заменить **без редактирования скрипта**, используя UCI-конфигурацию `/etc/config/netguard`. Имя UCI-пакета именно `netguard`, поскольку UCI не допускает дефис в идентификаторе пакета.

Готовый [пример конфигурации](examples/netguard) содержит два независимых списка:

- `list https 'имя|IPv4|TLS-хост|путь|ожидаемый_HTTP-код'` — для проверки HTTPS; вместо кода можно указать `-`, тогда проверяется только ответ сервера без признания endpoint исправным.
- `list dns 'имя|IPv4'` — для обычного DNS.

Каждый список заменяет соответствующие встроенные цели независимо от другого. Если список отсутствует, используются встроенные значения. Максимум — 12 записей на список; некорректные записи приводят к ошибке конфигурации, а не к незаметному переходу на другие адреса.

Для **проверки без записи на flash** можно загрузить пример в `/tmp` и указать отдельный каталог UCI:

```sh
mkdir -p /tmp/netguard-config
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/examples/netguard \
  -o /tmp/netguard-config/netguard
OWRT_NETGUARD_CONFIG_DIR=/tmp/netguard-config sh /tmp/owrt-netguard check
```

Это экспериментальная возможность: списки проверяются по указанному порядку, опрос прекращается после двух строгих HTTPS-успехов и двух DNS-ответов. Для сайтов из «белых списков», личного кабинета провайдера и captive portal **специальная оценка ограниченного доступа пока не реализована** — не добавляйте их как обычные `200`-проверки, иначе возможен ложный `HEALTHY_SAMPLED`.

Офлайн smoke-тесты: `sh tests/smoke.sh ./owrt-netguard` (15 сценариев, включая некорректную UCI-конфигурацию).

### Экспериментальная корреляция инцидентов

Отдельная [shell-библиотека состояний](lib/netguard-state.sh) принимает нормализованные результаты `check` и определяет моменты открытия, уточнения и закрытия инцидента. Предварительные пороги — три последовательных отказа одного класса и два подтверждённых успешных наблюдения. Уже открытый WAN-инцидент не дублируется при последующих ошибках DNS. Недостаток данных (`UNKNOWN_ROUTE`) не считается восстановлением.

Это **исолированный прототип в оперативной памяти**, ещё не подключённый к `check` или фоновому сервису. Он не создаёт журнал на flash, не рассчитывает длительность и не сохраняет состояния после перезагрузки. Тест последовательностей: `sh tests/state.sh ./lib/netguard-state.sh`. Добавление теста в репозиторий не означает его успешного выполнения на OpenWrt.

## Направления разработки

### Мониторинг и диагностика

Планируемые возможности:

- проверка состояния WAN, интерфейсов и маршрутов;
- независимая оценка внешней IP-связности, не опирающаяся только на локальный DNS;
- раздельные проверки внешнего и локального DNS;
- выявление деградации и сопоставление связанных ошибок в один инцидент;
- история отказов, времени восстановления и результатов диагностики;
- уведомления о проблемах и восстановлении соединения.

Диагноз должен основываться на наблюдаемых фактах. Например, отсутствие доступа к внешним адресам ещё не доказывает, что неисправность возникла именно у провайдера.

### Расширяемость

Базовый монитор не должен требовать Podkop, sing-box или определённый VPN. В дальнейшем предполагаются необязательные адаптеры для диагностики отдельных сетевых компонентов.

### Восстановление связности

В перспективе проект может получить отдельный, **явно включаемый** режим Recovery: контролируемые действия при подтверждённой локальной неисправности, проверку результата и безопасный откат.

По умолчанию предполагается режим **только наблюдения**. Аварийный выход напрямую через провайдера (fail-open) не должен происходить без разрешения пользователя: это может нарушить ожидаемую политику маршрутизации и конфиденциальности. Для защищённого трафика должны быть предусмотрены ограничительные политики.

**Recovery пока не реализован.**

## Совместимость

Целевые версии для разработки и проверки:

- OpenWrt **24.10.x** (`opkg`);
- OpenWrt **25.12.x** (`apk`).

Планируется лёгкая реализация с опорой на стандартные механизмы OpenWrt, без обязательных тяжёлых runtime-зависимостей.

Это целевая матрица совместимости, **не заявление о полностью протестированной поддержке**: опубликован экспериментальный скрипт, но стабильного релиза пока нет. OpenWrt 24.10.5 проверялась на AX6000 с прежней итерацией прототипа; OpenWrt 25.12 пока не проверялась ни в QEMU, ни на физическом устройстве.

## Принципы

- Независимость от конкретного VPN, прокси и сторонней системы маршрутизации.
- Разделение сетевой диагностики и действий по восстановлению.
- Минимальная нагрузка на роутер и аккуратная работа с flash-памятью.
- Защита от ложных срабатываний и повторяющихся уведомлений.
- Отсутствие автоматических изменений маршрутизации в режиме мониторинга.
- Предсказуемое поведение при потере WAN, перезагрузке и восстановлении сети.

## Связанные проекты

`owrt-netguard` разрабатывается как самостоятельный инструмент. Он не заменяет:

- [podkop-vpn-failover](https://github.com/SVTagan/podkop-vpn-failover) — автоматическое переключение резервных AmneziaWG-туннелей в Podkop;
- [podkop-guard](https://github.com/SVTagan/podkop-guard) — сохранение проверенного Last Known Good состояния списков и кеша Podkop.

Интеграции с этими проектами возможны в будущем, но не являются обязательными для работы базового монитора.
