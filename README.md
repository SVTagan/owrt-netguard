# owrt-netguard

[English](README.en.md)

Небольшой независимый проект для OpenWrt, который я задумал, чтобы разобраться, почему пропадает интернет и на каком участке возникает проблема.

Идея появилась из вполне практической ситуации: на моих роутерах несколько раз пропадала связь, а диагностика [Podkop](https://github.com/itdoginfo/podkop) сообщала об ошибках DNS. В итоге причиной оказывались неполадки у провайдера. При этом похожие симптомы могут возникать из-за самого роутера, DNS, маршрутизации или VPN — и по сообщению одного сервиса не всегда понятно, с чего начинать поиск.

В OpenWrt уже есть инструменты для проверки доступности, сбора статистики и восстановления соединений. Они решают свои задачи, но мне хотелось другого: сопоставлять проверки на разных уровнях, отличать причину отказа от сопутствующих ошибок и сохранять историю инцидентов. Так появилась идея NetGuard.

Хотя задача выросла из конфигураций с Podkop и VPN, делать ещё один инструмент только для Podkop я не хотел. NetGuard задуман как самостоятельный монитор для разных конфигураций OpenWrt, который со временем можно будет расширить безопасными механизмами восстановления связности.

## Статус

**В репозитории находится экспериментальное диагностическое ядро, RAM-автомат инцидентов, ручной монитор и сервисный worker с procd-интеграцией. Стабильного релиза и установщика пока нет.**

Команда `owrt-netguard check` выполняет однократную диагностику IPv4. Отдельный `netguard-worker` предназначен для периодического наблюдения, но пока не устанавливается автоматически и по умолчанию отключён. Код не перезапускает сетевые службы, не меняет DNS, firewall или маршрутизацию.

### Пробная проверка

На роутере с установленным `curl` можно загрузить текущий исходник в `/tmp` и запустить его через shell:

```sh
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/owrt-netguard \
  -o /tmp/owrt-netguard
sh /tmp/owrt-netguard check
```

Временный файл не добавляется в автозапуск и не устанавливается в систему. Если нужного компонента нет, команда завершится с сообщением об ошибке, но самостоятельно ничего устанавливать не будет. Для проверки другого логического WAN:

```sh
OWRT_NETGUARD_WAN=wan2 sh /tmp/owrt-netguard check
```

Прототип использует `ubus`, `jsonfilter`, `ip`, `curl`, `nslookup` с собственными параметрами таймаута (`-timeout`/`-retry`) и стандартные BusyBox-утилиты. `nft` используется необязательно, для проверки попадания адресов в набор Podkop.

Пока реализованы проверка состояния WAN, несколько HTTPS-целей через явно заданные IP с проверкой TLS и несколько независимых DNS-резолверов. Для HTTPS **доступность TLS/HTTP-сервера и исправность контрольного endpoint — разные результаты**: например, HTTP 404 от Яндекса показывает, что сервер отвечает, но не считается успешным контрольным ответом. Строгие проверки сейчас используют Cloudflare (`/cdn-cgi/trace`, HTTP 200) и Google DNS API (`/resolve?name=example.com&type=A`, HTTP 200); Яндекс и Quad9 пока дают только дополнительный сигнал доступности TLS/HTTP, без требования к коду ответа. После двух подтверждённых успешных HTTPS-ответов дополнительные цели не опрашиваются; DNS-проверки аналогично прекращаются после двух ответов. При ошибках опрос расширяется.

Доступные статусы включают `HEALTHY_SAMPLED` (только проверенная выборка, не гарантия доступа ко всему интернету), `WAN_INITIALIZING` (netifd ещё настраивает WAN), `WAN_NO_L3`, `PARTIAL_REACHABILITY`, `LOCAL_DNS_UNAVAILABLE`, `EXTERNAL_DNS_UNCONFIRMED`, `DNS_PATH_UNCONFIRMED` и `UNKNOWN_ROUTE`. Недоступные или пропущенные цели не позволяют безоговорочно считать всю сеть исправной.

**Важные ограничения:** реализована только IPv4-диагностика; UCI позволяет задать собственные HTTPS/DNS-цели. Сбой всех выбранных целей не доказывает аварию провайдера; ограниченный доступ из-за неоплаты или captive portal пока отдельно не определяется. `curl --interface`, закреплённые IP и обычная таблица маршрутов не гарантируют обход nftables/PBR; внешний `nslookup` не привязан строго к WAN. История инцидентов, уведомления и Recovery не реализованы. Предыдущая версия диагностических компонентов прошла испытания на AX6000/OpenWrt 24.10.5, новая логика ожидания WAN прошла проверку на физическом AX6000 (3 цикла) и в QEMU/OpenWrt 25.12.5.

Активирован ручной [GitHub Actions QEMU-стенд OpenWrt 25.12.5](tests/ci/README.md). [Запуски №1](https://github.com/SVTagan/owrt-netguard/actions/runs/38820425380), [№2](https://github.com/SVTagan/owrt-netguard/actions/runs/39973225284), [№3](https://github.com/SVTagan/owrt-netguard/actions/runs/39990869415) и [№5](https://github.com/SVTagan/owrt-netguard/actions/runs/40030153822) завершились успешно. Запуск №4 остановился из-за недоступности индекса apk, а не из-за сбоя тестов. Третий прогон проверил 16 smoke-сценариев, 55 переходов, worker, procd, аудит WAN-пути, endpoint survey и загрузчик профилей с **настоящим UCI OpenWrt**. Обновлённый worker и загрузчик профилей проверены на AX6000. Новый движок групповых HTTPS-проверок успешно прошёл QEMU №5, но ещё не проверен на AX6000; аппаратных испытаний OpenWrt 25.12 не было.

### Собственные контрольные адреса (необязательно)

По умолчанию используются встроенные HTTPS- и DNS-цели. Их можно заменить **без редактирования скрипта**, используя UCI-конфигурацию `/etc/config/netguard`. Имя UCI-пакета именно `netguard`, поскольку UCI не допускает дефис в идентификаторе пакета.

Готовый [пример конфигурации](examples/netguard) содержит два независимых списка:

- `list https 'имя|IPv4|TLS-хост|путь|ожидаемый_HTTP-код'` — для проверки HTTPS; вместо кода можно указать `-`, тогда проверяется только ответ сервера без признания endpoint исправным.
- `list dns 'имя|IPv4'` — для обычного DNS.

Каждый список заменяет соответствующие встроенные цели независимо от другого. Если список отсутствует, используются встроенные значения. Максимум — 12 записей на список; некорректные записи приводят к ошибке конфигурации, а не к незаметному переходу на другие адреса.

Для **проверки без записи на flash** можно загрузить пример в `/tmp` и указать отдельный каталог UCI:

```sh
mkdir -p /tmp/netguard-config
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/examples/netguard \
  -o /tmp/netguard-config/netguard
OWRT_NETGUARD_CONFIG_DIR=/tmp/netguard-config sh /tmp/owrt-netguard check
```

Это экспериментальная возможность: списки проверяются по указанному порядку, опрос прекращается после двух строгих HTTPS-успехов и двух DNS-ответов. Для сайтов из «белых списков», личного кабинета провайдера и captive portal **специальная оценка ограниченного доступа пока не реализована** — не добавляйте их как обычные `200`-проверки, иначе возможен ложный `HEALTHY_SAMPLED`.

Офлайн smoke-тесты: `sh tests/smoke.sh ./owrt-netguard` (16 сценариев, включая настройку WAN и некорректную UCI-конфигурацию).

### Экспериментальная корреляция инцидентов

Отдельная [shell-библиотека состояний](lib/netguard-state.sh) принимает нормализованные результаты `check` и определяет моменты открытия, уточнения и закрытия инцидента. Предварительные пороги — три последовательных отказа одного класса и два подтверждённых успешных наблюдения. Уже открытый WAN-инцидент не дублируется при последующих ошибках DNS. Недостаток данных (`UNKNOWN_ROUTE`) не считается восстановлением.

Библиотека теперь соединяется с `check` через отдельный [ручной монитор](netguard-monitor). Он последовательно выполняет диагностические проверки, передаёт их результаты обработчику и завершается после заданного количества циклов. Это **не демон и не установленный сервис**: нет автозапуска, постоянного журнала на flash и восстановления состояния после перезагрузки. Пороги и интервалы пока экспериментальные.

Для запуска трёх циклов с 10-секундным интервалом на OpenWrt:

```sh
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/owrt-netguard -o /tmp/owrt-netguard
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/lib/netguard-state.sh -o /tmp/netguard-state.sh
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/netguard-monitor -o /tmp/netguard-monitor
sh /tmp/netguard-monitor 3 10
```

Требуется явно задать число циклов от 1 до 30; интервал необязателен (по умолчанию 30 секунд). Монитор выводит `SAMPLE`, `STATE` и при необходимости события `OPEN`, `RECLASSIFIED`, `RESOLVED`. Если сам `check` не смог выполнить диагностику, используется `PROBE_ERROR`: это неопределённое состояние, а не доказательство сетевой аварии. Все состояния находятся **только в оперативной памяти процесса**.

Тесты: `sh tests/state.sh ./lib/netguard-state.sh` и `sh tests/monitor.sh ./netguard-monitor ./lib/netguard-state.sh`. На реальном AX6000 под OpenWrt 24.10.5 библиотека успешно обработала **43 перехода**, а ручной монитор затем прошёл **три последовательных цикла** `HEALTHY_SAMPLED → HEALTHY` и завершился штатно. Негативные сценарии проверены имитационными тестами, но не воспроизводились отключением WAN. Новая логика `WAN_INITIALIZING`/`STARTUP_WAIT` успешно прошла [QEMU/OpenWrt 25.12.5 CI №2](https://github.com/SVTagan/owrt-netguard/actions/runs/39973225284). На физическом AX6000 эта итерация прошла ограниченный тест в трёх циклах при исправном WAN.

### Экспериментальный сервисный слой (пока не устанавливать)

Подготовлены [foreground worker](netguard-worker) и [init-скрипт procd](service/netguard.init). Запуск, остановка и повторный запуск под **настоящим procd** успешно проверены внутри QEMU/OpenWrt 25.12.5; установка в физический роутер ещё не проводилась. На данном этапе не копируйте init-скрипт в `/etc/init.d` и не включайте автозапуск.

Сервисная конфигурация в [примере UCI](examples/netguard) по умолчанию содержит `monitor_enabled=0`: даже ручной запуск init-скрипта без явного включения мониторинга не должен запускать worker. Предварительный интервал — 30 секунд после завершения предыдущей проверки; `startup_grace=90` секунд по умолчанию позволяет штатной сети подняться после запуска worker, не ожидая Podkop/VPN. После истечения grace продолжается обычное подтверждение отказов. В ограниченном ручном режиме grace по умолчанию отключён, но доступен через `NETGUARD_STARTUP_GRACE` (0–300). `procd` будет запускать worker на переднем плане, перезапуская его при аварийном выходе с ограничением частоты попыток.

Worker пишет только атомарный снимок последнего состояния в **RAM** (`/tmp/netguard-runtime/status`) и выводит события изменения инцидентов; историю каждой сетевой проверки на flash не пишет. После аварийного завершения снимок может устареть — пока это **не полноценная реализация команды `status`**.

Чтобы проверить новый worker **без установки сервиса**, скачайте его в `/tmp`, затем выполните ограниченные три цикла:

```sh
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/netguard-worker -o /tmp/netguard-worker
NETGUARD_CHECK_PATH=/tmp/owrt-netguard NETGUARD_STATE_PATH=/tmp/netguard-state.sh \
  sh /tmp/netguard-worker --cycles 3 10
cat /tmp/netguard-runtime/status
```

Для теста требуются актуальные `/tmp/owrt-netguard` и `/tmp/netguard-state.sh`, уже загруженные по инструкциям выше. `--forever` существует только для будущего явно разрешённого `procd`-запуска; **пока его на рабочем роутере не используйте**. Офлайн-сценарии: `sh tests/worker.sh ./netguard-worker ./lib/netguard-state.sh`. В QEMU/OpenWrt 25.12.5 успешно прошёл [тест жизненного цикла procd](tests/ci/procd-guest.sh): выключенный сервис → явное включение → RAM-состояние → остановка → повторный запуск. Во втором QEMU-прогоне новые тесты стартового периода и превышения его срока успешно выполнены. Worker теперь проверен на реальном Redmi AX6000 (OpenWrt 24.10.5): три цикла дали `HEALTHY_SAMPLED`, итоговый RAM-снимок показал `running=0`, `phase=HEALTHY`, `result=HEALTHY_SAMPLED`, `cycle=3`. Работа через `procd`, реальное аварийное завершение и постоянное хранение событий ещё не проверялись.

### Групповая HTTPS-диагностика: экспериментальный режим

Добавлена отдельная ручная команда [`netguard-profile-probe`](netguard-profile-probe), использующая загрузчик профилей без изменения старой `owrt-netguard check` или worker. Она делает ограниченные по времени и размеру HTTPS GET-запросы по выбранному профилю, проверяет HTTP-код, TLS и необязательный токен ответа, затем выводит **раздельные результаты** для `ru_base`, `ru_diverse` и `international`.

Ключевой принцип: `RU_REACHABLE_SAMPLED`, `RU_PARTIALLY_CONFIRMED`, `POSSIBLE_LIMITED_ACCESS`, `INTERNATIONAL_UNCONFIRMED` и прочие `PROFILE_OBSERVATION` — диагностические наблюдения, **не доказательство виновности провайдера**. Например, недоступность иностранных ресурсов не отменяет подтверждённой доступности российских. Ошибка DNS при `auto` не приравнивается к отказу WAN; для пользовательских закреплённых IP используется `curl --resolve`. Обычная проверка маршрута по-прежнему не исключает перехват nftables/PBR.

Команда требует явного выбора профиля либо временной UCI-конфигурации с `option profile`; при старом профиле `legacy` она отказывается от выполнения, чтобы случайно не изменить смысл штатной диагностики. Никаких изменений DNS, UCI, firewall, маршрутов и работающих служб нет. Максимум 12 endpoint по 8 секунд каждый, размер одного ответа — 32 КиБ. В автоматический worker пока **не интегрирована**.

Локальные [тесты](tests/profile-probe.sh) прошли в BusyBox `ash`, `dash`, `bash`, включая режим белых списков, отказ иностранных целей, неверный HTTP-body, DNS-ошибку при успешном закреплённом IP, расхождение маршрутов и TLS-ошибку. Тесты успешно прошли [QEMU-прогон №5](https://github.com/SVTagan/owrt-netguard/actions/runs/40030153822); реальных групповых HTTPS-испытаний модуля на AX6000 ещё не было. Подробнее — [архитектура профилей](docs/endpoint-profiles.md).

### Профили endpoint: экспериментальный загрузчик конфигурации

Первый этап профилей реализован в [`lib/netguard-profiles.sh`](lib/netguard-profiles.sh) и [`netguard-profiles`](netguard-profiles). Это **только проверка и отображение настроек**, а не новая реализация `owrt-netguard check`. Диагностическое ядро, старые `list https`/`list dns` и worker пока не изменены.

Профили `russia` (два исследовательских RU-кандидата Selectel и Timeweb), `international` (Google gstatic, Apple, Mozilla) и `custom` (пользовательские цели) выбираются явно. Новое поле `list https_target` имеет формат `группа|имя|TLS-хост|IPv4-или-auto|путь|HTTP-код|токен-или--`. `auto` использует системный DNS; закреплённый IPv4 отделяет HTTPS-проверку от локального DNS. Парсер проверяет синтаксис и дубликаты, максимум 12 целей. Для Russia пока выдаётся предупреждение `LIMITED_TARGET_DIVERSITY`: два проверенных на одной сети ресурса нельзя считать устойчивым универсальным набором для РФ.

Пример конфигурации [`examples/netguard-profiles.preview`](examples/netguard-profiles.preview) предназначен **исключительно для просмотра из /tmp**; копировать его в `/etc/config/netguard` пока нельзя, поскольку рабочий `check` ещё не читает новый формат и продолжит использовать старые цели. Отсутствие `option profile` сохраняет `LEGACY_UNCHANGED`. Схема и границы применения описаны в [`docs/endpoint-profiles.md`](docs/endpoint-profiles.md).

Локальные офлайн-тесты [`tests/profiles.sh`](tests/profiles.sh) прошли под BusyBox `ash` 1.37, `dash` и `bash`; и в [QEMU-прогоне №3](https://github.com/SVTagan/owrt-netguard/actions/runs/39990869415), включая чтение настроек настоящим UCI. Загрузчик профилей проверен на AX6000/OpenWrt 24.10.5 с временным UCI-файлом в `/tmp` (две цели Selectel и Timeweb, `LIMITED_TARGET_DIVERSITY`); групповой HTTPS-движок на AX6000 пока не запускался.

### Исследовательская проверка endpoint для РФ и международных сетей

Подготовлен отдельный **ручной**, не участвующий в штатном мониторинге скрипт [`netguard-endpoint-survey`](netguard-endpoint-survey). Это инструмент **отбора** контрольных ресурсов, а не новые production-defaults. Российские сайты могут отдавать redirect и большие страницы; их ответы, CDN/IP и пригодность ещё нужно проверить на реальных операторах. Международные адреса используются для сравнения, **не для доказательства аварии провайдера при блокировке**.

```sh
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/netguard-endpoint-survey -o /tmp/netguard-endpoint-survey
sh -n /tmp/netguard-endpoint-survey
sh /tmp/netguard-endpoint-survey --profile all
```

Есть фильтры `--profile ru` (пять российских ресурсов в группах `ru_base` и `ru_diverse`) и `--profile international` (три зарубежных проверочных ресурса из VPN Failover). **Эти группы пока не являются профилями рабочего NetGuard.** В текущей кандидатной группе `ru_base` — `ya.ru`, `mail.ru`, в `ru_diverse` — `reg.ru`, `nic.ru`, `timeweb.com`. В международной группе — `www.gstatic.com/generate_204` (HTTP 204), `captive.apple.com/hotspot-detect.html` (HTTP 200 + `Success`), `detectportal.firefox.com/success.txt` (HTTP 200 + `success`).

Скрипт применяет `curl -4 --interface if!<wan-device> --noproxy '*'`, проверяет TLS и выводит фактический адрес подключения (`remote_ip`), HTTP-код, время, объём ответа и **немаркированный** маршрут к полученному IP. Системный DNS остаётся прежним; перенаправления не выполняются, максимальное время ответа — 8 секунд, размер тела ограничен 128 КиБ. `REDIRECT`, `BODY_LIMIT`, `CONTRACT_MISMATCH` и `ERROR` — разные признаки, они **не равнозначны отключению интернета**. Даже `MATCHED` не удостоверяет физический путь через провайдера при наличии nftables/PBR, а лишь выполнение HTTP/TLS-критериев отдельного endpoint.

Для эксперимента со **своими** кандидатами предусмотрен `--file /tmp/targets`: строки `group|name|https://host/path|expected_http|expected_body`, группировка `ru_base`/`ru_diverse`/`international`, HTTP-критерии `200`, `204`, `2xx`, `any`, значение `-` вместо проверки тела. Не более 16 целей. Файл задаётся самим пользователем: скрипт его не изменяет. UCI-профили рабочего мониторинга `Russia`/`International`/`Custom` ещё **не реализованы** — их проектируем после проверки кандидатов.

Утилита не меняет UCI, DNS, сетевые интерфейсы или firewall, не устанавливает службу, не пишет результаты на flash. Только HTTPS GET к перечисленным публичным ресурсам и кратковременный файл тела в `/tmp` для точной проверки токенов. Офлайн-тест `sh tests/endpoint-survey.sh ./netguard-endpoint-survey` **успешно выполнен локально** в BusyBox `ash` 1.37, `dash` и `bash` на очищенной версии [коммита `476eb67`](https://github.com/SVTagan/owrt-netguard/commit/476eb67420188034818d303bbdd7e6df7a0734c4). Ранее опубликованный скрипт содержал дублированные блоки и давал синтаксические ошибки; использовать старые pinned-коммиты нельзя. Исправленный survey прошёл QEMU-прогон №3 и реальные HTTPS-испытания на AX6000. Испытания в одной сети не гарантируют доступности endpoint у других операторов РФ.

### Экспериментальный аудит WAN-пути

Добавлена отдельная ручная команда [`netguard-path-audit`](netguard-path-audit). Это **чтение диагностических признаков**, а не доказательство фактического пути каждого пакета. Утилита не зависит от Podkop и других пакетов; на чистом OpenWrt она работает с `ubus`, `jsonfilter`, `ip` и, если доступен, `nft`. Политики и таблицы nftables **не изменяются**.

```sh
curl -fsSL https://raw.githubusercontent.com/SVTagan/owrt-netguard/main/netguard-path-audit -o /tmp/netguard-path-audit
sh -n /tmp/netguard-path-audit
sh /tmp/netguard-path-audit
```

По умолчанию проверяется маршрут к `1.1.1.1` (IP контрольного HTTPS-ресурса), но можно передать другой IPv4-адрес первым аргументом. Для другого логического WAN задайте `OWRT_NETGUARD_WAN`. Аудит показывает совпадение немаркированного маршрута с WAN, наличие дополнительных IPv4 policy rules и исходящих nftables `route`/`nat`-цепочек. Признаки дополнительной маршрутизации не означают, что конкретный контрольный пакет был перехвачен.

`PATH_AUDIT: ROUTE_MATCH_ONLY` **не означает** «WAN-путь достоверно проверен»: локальные пакеты могут обрабатываться netfilter OUTPUT, правилами policy routing и другими системными механизмами. `ROUTE_MISMATCH` означает лишь то, что маршрут без дополнительных меток выбрал другое устройство; `INSUFFICIENT_EVIDENCE` — отсутствие достаточных сведений. Сам аудит не выполняет сетевых запросов и не должен автоматически превращать эти признаки в «виноват провайдер».

На этом этапе утилита **не встроена в циклический worker** и не создаёт дополнительных постоянных опросов nftables. Имитационные тесты `sh tests/path-audit.sh ./netguard-path-audit` успешно выполнены в QEMU-прогоне №3; ручной аудит также был выполнен на AX6000.

## Направления разработки

### Мониторинг и диагностика

Планируемые возможности:

- проверка состояния WAN, интерфейсов и маршрутов;
- независимая оценка внешней IP-связности, не опирающаяся только на локальный DNS;
- раздельные проверки внешнего и локального DNS;
- выявление деградации и сопоставление связанных ошибок в один инцидент;
- история отказов, времени восстановления и результатов диагностики;
- уведомления о проблемах и восстановлении соединения.

Диагноз должен основываться на наблюдаемых фактах. Например, отсутствие доступа к внешним адресам ещё не доказывает, что неисправность возникла именно у провайдера.

### Расширяемость

Базовый монитор не должен требовать Podkop, sing-box или определённый VPN. В дальнейшем предполагаются необязательные адаптеры для диагностики отдельных сетевых компонентов.

### Восстановление связности

В перспективе проект может получить отдельный, **явно включаемый** режим Recovery: контролируемые действия при подтверждённой локальной неисправности, проверку результата и безопасный откат.

По умолчанию предполагается режим **только наблюдения**. Аварийный выход напрямую через провайдера (fail-open) не должен происходить без разрешения пользователя: это может нарушить ожидаемую политику маршрутизации и конфиденциальности. Для защищённого трафика должны быть предусмотрены ограничительные политики.

**Recovery пока не реализован.**

## Совместимость

Целевые версии для разработки и проверки:

- OpenWrt **24.10.x** (`opkg`);
- OpenWrt **25.12.x** (`apk`).

Планируется лёгкая реализация с опорой на стандартные механизмы OpenWrt, без обязательных тяжёлых runtime-зависимостей.

Это целевая матрица совместимости, **не заявление о полностью протестированной поддержке**. На физическом AX6000/OpenWrt 24.10.5 ранее проверены диагностика, RAM-автомат, монитор и ограниченный worker. На QEMU/OpenWrt 25.12.5 ранее прошли smoke, state, worker и procd-тесты. Новая стартовая логика прошла регрессию в QEMU/OpenWrt 25.12.5 и ограниченный тест на физическом AX6000; физическая OpenWrt 25.12 также не проверена.

## Принципы

- Независимость от конкретного VPN, прокси и сторонней системы маршрутизации.
- Разделение сетевой диагностики и действий по восстановлению.
- Минимальная нагрузка на роутер и аккуратная работа с flash-памятью.
- Защита от ложных срабатываний и повторяющихся уведомлений.
- Отсутствие автоматических изменений маршрутизации в режиме мониторинга.
- Предсказуемое поведение при потере WAN, перезагрузке и восстановлении сети.

## Связанные проекты

`owrt-netguard` разрабатывается как самостоятельный инструмент. Он не заменяет:

- [podkop-vpn-failover](https://github.com/SVTagan/podkop-vpn-failover) — автоматическое переключение резервных AmneziaWG-туннелей в Podkop;
- [podkop-guard](https://github.com/SVTagan/podkop-guard) — сохранение проверенного Last Known Good состояния списков и кеша Podkop.

Интеграции с этими проектами возможны в будущем, но не являются обязательными для работы базового монитора.
